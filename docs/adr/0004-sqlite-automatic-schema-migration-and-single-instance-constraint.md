# ADR-0004: SQLite PRAGMA 自動マイグレーションと単一インスタンス制約 (PostgreSQL 移行パス)

- **ステータス**: Accepted
- **決定日**: 2026-09-17

---

## 1. 背景と課題 (Context & Problem Statement)

本システムでは、ユーザーの過去問解答履歴、正誤記録、弱点分析データ、および中断された演習セッションの状態を永続化する必要がある。

永続化層の設計において、以下の課題が存在した：
1. **初期フェーズの軽量性と独立性**:
   外部のマネージドリレーショナルデータベース（Cloud SQL 等）は高価であり、ローカル開発や小規模運用において接続設定や管理コストが過大となる。外部依存ゼロでファイルベースで稼働できる構成が望ましい。
2. **スキーマ変更への追随性 (Zero Overhead Migration)**:
   演習セッション再開機能や複合インデックスの追加など、データモデルの進化に対して Alembic などの重厚な外部マイグレーションツールを導入せず、アプリケーション起動時に自動適用される仕組みが必要。
3. **ファイルベース DB 特有の同時実行制約**:
   SQLite はファイルロック機構に基づくため、コンテナがマルチインスタンスで並列稼働するとデータベースファイルへの書き込み競合（`database is locked`）やデータ破損が発生するリスクがある。

---

## 2. 検討した選択肢 (Considered Options)

1. **選択肢 A: SQLite ＋ WAL モード ＋ `PRAGMA user_version` 自動マイグレーション ＋ 単一インスタンス制約（採用）**
2. **選択肢 B: Cloud SQL (PostgreSQL) の初期からの導入**
3. **選択肢 C: NoSQL / ドキュメント指向 DB (Firestore) の採用**

---

## 3. 決定事項 (Decision)

**選択肢 A を採用する。**

### 3.1. SQLite ＋ WAL モードによる軽量永続化
解答履歴およびセッション管理のストレージとして SQLite を採用し、以下の PRAGMA 設定で初期化する：
- `PRAGMA journal_mode = WAL`: 読み取りと書き込みの並行性を極大化。
- `PRAGMA synchronous = NORMAL`: 高スループットかつ安全なディスク同期。
- `PRAGMA busy_timeout = 5000`: 一時的なロック競合時のリトライ許容時間を 5 秒に設定。

### 3.2. `PRAGMA user_version` による外部依存ゼロの自動マイグレーション
外部ツールに依存せず、SQLite ネイティブの `user_version` を利用した自動マイグレーションエンジン（`DatabaseMigrator`）を実装する：
- アプリケーション起動時に現在の `user_version` を検知。
- 定義されたマイグレーション関数（V1: 基本履歴テーブル → V2: 弱点分析用インデックス → V3: 中断セッション再開テーブル）を単一トランザクション内で逐次適用。
- 適用完了後に `PRAGMA user_version` を更新。失敗時は自動ロールバック。

### 3.3. 単一インスタンス制約 (Single-Instance Constraint) の明示
Cloud Run 上で SQLite を GCS FUSE 経由でマウント運用する場合、ファイルロック競合を物理防止するため、Cloud Run のスケーリング設定を **`maxScale: 1`** に厳格制限する。

### 3.4. 将来の PostgreSQL / Cloud SQL 移行パスの担保
Repository パターン（`IHistoryRepository`）を徹底することで、ドメイン層およびアプリケーション層は SQLite の具象実装に一切依存しない設計とする。
将来的にマルチユーザー・マルチインスタンス運用へ移行する際は、`PostgreSQLHistoryRepository` を新規実装して依存性注入（DI）コンテナで差し替えるだけで、上位レイヤーに一切の変更を加えることなく移行できる構造を保証する。

---

## 4. 影響と結果 (Consequences)

### ポジティブな影響
- **ゼロ構成での即時稼働**: ローカル開発時も本番環境も、外部 DB サーバー不要で直ちにテスト・稼働可能。
- **堅牢なスキーマ進化**: アプリケーション起動時にスキーマが自動同期され、手動マイグレーション漏れのリスクが根絶される。
- **将来への投資保護**: クリーンなリポジトリ抽象化により、将来の大規模化・PostgreSQL 移行がコード破壊なしで可能。

### トレードオフ・留意点
- Cloud Run の最大インスタンス数が 1 に制限される。高トラフィック化により水平スケーリングが必要となった段階で、計画された PostgreSQL 移行パスを発動する。
